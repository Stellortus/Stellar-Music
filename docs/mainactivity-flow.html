01 · 启动与登录

  • 自动 · 顺序MainActivity.onCreate()：准备应用基础环境
    • super.onCreate(savedInstanceState)：执行 Activity 基类初始化。
    • ToastManager.init(applicationContext)：保存 Toast 所需的应用 Context。
    • AuthPreferences.init(applicationContext)：准备登录信息的 SharedPreferences。
    • TrackManager.init()、PlaylistManager.init()：构建各自的 Room 数据库实例；这里没有发起歌曲或歌单网络请求。
    • enableEdgeToEdge()：启用内容延伸到系统栏区域的布局方式。
    • setContent { … }：开始构建 Compose 界面。
  • 自动setContent：建立 Compose 根节点
    • CompositionLocalProvider(LocalAuthPreferences provides AuthPreferences)：让子组件可通过 CompositionLocal 获取登录信息对象。
    • StellarMusicTheme：提供颜色、字体、形状和间距等主题配置。
    • MusicApp()：管理根登录状态，并决定显示哪个页面。
  • 自动MusicApp：先根据本地登录信息决定初始画面
    • 有非空 token、存在 userId，且 sessionExpired == false → Authenticated → 立即显示主界面。
    • 其他情况 → Loading → 显示“正在登录…”。
    • 因此，本地信息完整时，主页可以先出现，服务器登录校验随后异步完成。
  • 自动 · 异步LaunchedEffect(verifyAttempt)：向服务器校验登录
    • 没有 token → clearSession() → Unauthenticated → 显示登录／注册页面。
    • 有 token → 记录当前 token → 调用 AuthApi.me()；缺少 userId 时保持加载画面。
    • 校验成功
      • 如果 token 已改变或会话已失效，忽略本次结果，避免旧响应覆盖新会话。
      • 如果原 userId 与服务器返回的 id 不同，先显示加载状态，并清理原账号的歌曲、歌单缓存。
      • 再次确认 token 和会话状态 → 保存 username、userId → 两个 Manager 调用 startSession() → 显示主界面。
    • 校验失败
      • 协程取消 → 继续抛出 CancellationException。
      • token 已改变 → 忽略旧请求错误。
      • 401 → Toast 提示登录失效 → 设置 sessionExpired = true。
      • 其他错误 → Toast 提示；本地仍有 token 和 userId 时保留主界面，否则显示 NetworkErrorScreen。
      • 网络错误页：点击“重试”增加 verifyAttempt，重新校验；点击“进入登录页”触发会话清理。
  • 用户操作登录／注册成功：保存新会话，再进入主页
    • 校验表单 → 调用 AuthApi.login() 或 AuthApi.register()。
    • saveAuth()：先清理旧会话 → 保存 token、userId、username → 两个 Manager 启动会话。
    • onLoggedIn：切换到 Authenticated，并增加 verifyAttempt，再执行一次服务器校验。
  • 持续监听LaunchedEffect(Unit)：处理会话失效与退出登录
    • 持续收集 AuthPreferences.sessionExpired。
    • 收到 true → 切换为 Loading → clearSession() → 切换为 Unauthenticated。
    • clearSession() 在 NonCancellable 中执行：取消并等待 Manager 任务结束 → 清空两个 Room 缓存 → 清空登录信息 → 将失效标记重置为 false。
    • 主界面退出组合时，其播放器通过 onDispose 释放，详见第 04 部分。

02 · 主界面与四个页面

  • 进入主界面MainScreen：创建公共状态与布局
    • 默认选中 HomeTab；通过 remember 创建一份 MusicPlayerState，内部创建播放控制器和 ExoPlayer。
    • 初始 currentTrack == null，不自动播放，底部播放器条暂不显示。
    • queueVisible 用 rememberSaveable 保存播放列表的显示状态。
    • PlaybackQueueHost 包住 StellarScaffold；Scaffold 底部依次放播放器条和导航栏。
    • 点击底部导航 → 关闭播放列表浮层 → 更新选中项 → 显示对应页面；播放器对象保留。
    • 监听 playbackError → Toast 显示错误 → 清空错误状态，避免重复提示。
  • 自动检查 · 用户确认下载AppUpdatePrompt：检查应用更新
    • 进入该组合后，异步查询最新版本号，与 BuildConfig.VERSION_CODE 比较。
    • 版本较新 → 获取版本名称 → 显示更新弹窗；无效版本号或检查失败写入日志。
    • 点击“立即更新” → 在 IO 中交给系统 DownloadManager 下载 APK → Toast 提示并关闭弹窗。
    • 下载完成后由用户从系统通知打开安装包；点击“暂不更新”只关闭弹窗。
  • 首页HomeScreen：歌曲加载、搜索与点播
    • 自动加载与分页
      • LaunchedEffect(retryTick) 从偏移 0 开始，通过 TrackManager.getMusicList() 获取首批歌曲。
      • 加载成功 → 显示歌曲列表并更新偏移；失败 → Toast 提示并提供重试。
      • snapshotFlow 监听列表末项进入可见区域 → 请求下一页；通过加载状态和结束标记避免重复请求。
      • 按歌曲 id 排除已有数据；空页或没有新歌曲时标记结束。一页不满屏时可继续补下一页。
    • 搜索、点击和长按
      • 提交非空关键词 → 更新 TrackSearchState → 显示搜索页 → 调用歌曲搜索接口。
      • 搜索状态由泛型 SearchState<Track> 管理：关键词、结果、加载、失败、取消和响应版本判断。
      • 返回首页会取消当前搜索；失败可以重试。
      • 点击首页或搜索结果中的歌曲 → player.play(track) → 创建大小为 1 的临时队列，进入统一播放流程。
      • 长按歌曲 → TrackDetails → 可打开 AddToPlaylistDialog，选择目标歌单并添加歌曲。
  • 歌单PlaylistScreen：列表、搜索和详情
    • NavHost 管理歌单列表、歌单搜索、歌单详情；搜索状态和列表滚动状态由外层保存。
    • 列表进入后通过 PlaylistManager.listPlaylists() 加载歌单；搜索通过 PlaylistSearchState 调用歌单搜索接口。
    • 点击歌单名称／条目进入详情；点击播放封面调用 player.togglePlaylist(id)。
    • 详情通过 getPlaylist(id) 加载歌曲，UI 按歌曲 id 去重。
    • 详情点击歌曲 → 将完整歌曲列表、所选 index 和歌单 id 传给 playPlaylist()，从该歌曲开始播放。
    • 详情点击播放封面 → 使用已加载列表调用 togglePlaylist()。
    • 按权限提供创建、重命名、删除、公开状态切换和添加歌曲操作。
    • 添加歌曲候选通过 TrackManager.getAllMusicList() 分页获取，默认最多 500 首，并排除歌单已有歌曲。
    • 重命名请求将 public 留空，由 Manager 获取最新公开状态后提交，避免使用过期值。
  • 上传UploadScreen：用户选择后才执行上传
    • 点击“选择音乐文件” → 系统文件选择器筛选 audio/*；取消选择则直接返回。
    • 选中文件 → Uploading → 在 IO 中把 URI 内容复制到应用缓存目录 → NetworkService.upload(file)。
    • 成功显示文件名；失败 Toast 提示；进入上传请求后通过 finally 删除临时文件。
    • 外层 finally 将仍处于 Uploading 的状态还原为 Idle；上传期间禁用选择按钮。
  • 个人ProfileScreen：展示账号与退出
    • 展示当前 username、userId 和应用版本。
    • 点击退出 → 调用登出接口 → 成功后触发 onLogout() → 设置会话失效标记，由根节点统一清理并回到登录页。
    • 登出请求失败 → 提示错误，保留当前页面。

切换底部标签页时，公共播放器保留；被移出组合的页面，其 remember 状态与页面协程通常随之销毁。页面内导航保存的状态取决于对应 NavHost 和外层状态的生命周期。

03 · 统一播放流程

调用链：UI → MusicPlayerState → PlaylistPlaybackController → startTrack() → StreamPlayer → ExoPlayer。播放器回调再更新 Compose 状态。
  • 用户操作MusicPlayerState：接收统一的播放入口
    • 首页 play(track) → 控制器转为 playPlaylist(listOf(track), 0, null)；临时队列仅在当前播放会话中存在，不创建服务器歌单。
    • 歌单歌曲 playPlaylist(tracks, index, sourcePlaylistId) → 使用原歌单的歌曲快照与所选位置。
    • togglePlaylist(id, snapshot)：如果正在播放这个来源歌单，就切换暂停／继续；否则使用快照或按 id 加载后播放。
  • 控制逻辑PlaylistPlaybackController：管理队列、请求和播放顺序
    • cancelRequest()：增加 revision、取消旧 Job 并清空引用；异步返回时核对 revision，防止先前选择覆盖最新选择。
    • 如果需要远程加载歌单，加载期间保留原播放；加载失败提示错误。
    • startPlaylist()：空列表提示错误并保留原播放；有效列表复制为本次播放快照。
    • 初始化 SequentialOrder 的大小，以及 ShuffleOrder、RepeatOneOrder 各自保存的固定排列。
    • 随机排列以起播歌曲开头，其余索引打乱一次；两个排列策略各保存数组副本，后续切歌不累积历史。
    • 保存来源歌单 id → 调用 playResolvedIndex(startIndex)。
    • playResolvedIndex(target)：校验索引 → 同步三个策略的 index → 启用自动续播 → 发布队列与当前索引 → 调用 onPlay(track)。
  • 当前默认SequentialOrder：顺序循环；另外两个策略已准备
    • 当前 activeOrder 固定为 SequentialOrder，没有播放顺序切换按钮。
    • next()：(index + 1) % size；previous()：(index - 1 + size) % size。
    • step() 用于自然播放结束，顺序循环中等同于 next()；大小为 1 的队列会重复播放同一首。
    • ShuffleOrder：next／previous 沿固定 order 前后移动，首尾循环，step 同 next。
    • RepeatOneOrder：手动前后切换沿固定排列；step 返回当前索引，重复当前歌曲。
    • 策略函数只计算目标索引；真正同步 index、更新队列高亮和开始播放都由控制器统一提交。
    • 控制器已有手动 next／previous 方法，当前页面没有新增对应按钮或模式切换入口。
  • 开始播放startTrack → StreamPlayer → ExoPlayer
    • MusicPlayerState.startTrack()：更新 currentTrack，清零位置和时长，清空拖动预览与错误。
    • StreamPlayer.play(track.id)：从歌曲 id 构造播放 URI → setMediaItem() → prepare() → play()。
    • 音频通过带认证的流数据源读取；媒体缓存由 StreamCache 提供。
    • onPlayWhenReadyChanged 更新“用户是否要求播放”；onIsPlayingChanged 更新“目前是否实际播放”。缓冲时两者可能不同。
    • 实际播放时每 250ms 回传当前位置和时长；停止实际播放时取消进度循环。
    • 这些 Compose 可观察状态改变后，相关 UI 更新：歌曲信息、播放图标、封面动画、进度和队列高亮。
  • 用户操作暂停、进度拖动和当前播放列表
    • 暂停／继续 → MusicPlayerState.togglePause() → StreamPlayer.togglePause()；如播放器存在错误，继续播放前会重新 prepare。
    • 拖动进度 → onSeekPreview() 只更新预览位置；松手 → onSeekFinished() 才真正 seek。
    • 实际进度与目标差值小于 1000ms 时清掉预览，恢复显示实际进度。
    • 上滑显示播放列表的机制
      • 手势区域是播放器中的歌曲标题／歌手区域；累计向上拖动达到 48dp 后调用 onOpenQueue()。
      • 回调把 queueVisible 设为 true；进度 SeekBar 本身负责拖动进度。
      • PlaybackQueueHost 依据测量到的播放器顶部与根布局位置，在播放器上方放置列表；高度不超过根布局的 65%，且受可用空间限制。
      • 列表底部使用 StellarTheme.spacing.page 留出与播放器的间距。
      • 列表滑入／滑出、背景遮罩淡入／淡出均使用 240ms 动画。
      • PlaybackQueueSheet 显示队列，初始定位当前歌曲；点击其他歌曲索引切歌并保持列表打开。
      • 点击当前索引不重新播放，但会取消待完成的歌单选择请求。
      • 标题区域向下拖动 48dp、点击遮罩或按返回键 → 关闭列表。
  • 播放器回调自然结束与播放错误
    • ExoPlayer 到达 STATE_ENDED → 停止进度循环 → 回调 onCompleted()。
    • MusicPlayerState 清理播放位置和拖动预览 → 控制器在自动续播启用且队列非空时，调用 activeOrder.step()。
    • 得到目标索引 → 再次走 playResolvedIndex() → 同步状态并播放下一首；默认顺序首尾循环。
    • 播放器出错 → 暂停、停止进度循环、更新播放状态 → stopLoop() 停止自动续播 → 发布错误供 MainScreen 提示。
    • 后续通过有效的队列播放操作提交歌曲时，控制器会重新启用自动续播。

04 · 网络、缓存与生命周期

  • 按请求触发网络认证与错误传递
    • 业务 API 通过 Ktor 客户端请求；认证插件在需要时添加 Authorization: Bearer …。
    • ensureSuccess() 对非 2xx 抛出 ApiException；401 请求所用认证仍对应当前 token 时，标记会话失效。
    • 根节点监听到失效后统一清理会话，避免每个业务页面自行跳转登录。
    • 音频使用单独的 AuthStreamDataSource 与 OkHttp 认证拦截器；不经过业务 API 的同一套 401 处理函数。
    • 应用更新查询使用不携带业务认证的请求。
  • 读取数据Room 元数据缓存：TrackManager 与 PlaylistManager
    • 歌曲分页存入 tracks.db，歌单列表和详情存入 playlists.db；保存的是业务数据的 JSON，不是音频文件。
    • 普通读取 readCached()
      • 先查询 Room；有缓存则立即返回旧快照，同时启动会话作用域内的后台同步。
      • 没有缓存则等待同步完成，再从 Room 读取保存后的结果。
      • 同一个 key 的同步任务通过 pending 共享；互斥锁协调读写请求。
      • 任务完成后，在锁内确认映射仍是自己，再移除对应 key；后台非取消错误写入日志。
      • 后台写入缓存不会直接替换页面已经持有的普通列表快照；页面再次读取时才能拿到更新值。
    • 明确刷新 readFresh()
      • forceRefresh = true 时使用：等待网络获取 → 写入 Room → 读回保存结果。
      • 与歌单修改使用同一个互斥锁；刷新失败抛出错误，不返回旧缓存伪装成功。
      • 页面保留强制刷新标记，直到一次刷新成功后再清除。
  • 用户修改歌单变更：服务端结果与本地同步
    • Manager 在会话作用域内通过互斥锁串行处理修改；执行服务端操作后更新本地歌单缓存。
    • handlePlaylistChange() 统一处理操作结果。
    • 全部成功 → 关闭对应操作弹窗并刷新显示。
    • 普通请求失败 → 提示错误，保留可重试的操作界面。
    • 服务端操作成功但缓存同步失败 → 报告“操作已成功，列表同步失败，请稍后刷新” → 按已提交处理关闭弹窗，并要求后续强制刷新。
  • 异步任务取消与过期结果保护
    • runCatchingCancellable() 保留普通异常为 Result，但继续抛出取消异常，并在执行前后检查协程是否有效。
    • 各提交／加载流程通过 finally 复位 loading、submitting 等状态。
    • SearchState 与播放控制器除了取消 Job，还使用 revision 校验，防止过期请求回写新状态。
    • 页面离开组合会取消其页面协程；Manager 的缓存同步和修改任务属于会话作用域，可能继续执行。
    • 退出会话时 Manager 取消并等待这些任务，再清空数据库，防止旧任务之后写回。
  • 音频数据StreamCache：独立的媒体缓存
    • 播放器构建数据源时创建或复用进程内的 SimpleCache 单例。
    • 目录为应用 cacheDir/track_cache，使用 LRU 淘汰，容量上限 512MiB。
    • 数据源优先使用媒体缓存，缺失部分从带认证的上游流读取。
    • 这部分与 Room 元数据缓存分开；当前 clearSession() 没有清理它，播放器 release 也没有显式释放该单例。
  • 离开主界面DisposableEffect.onDispose：释放播放资源
    • MusicPlayerState.release() → 控制器取消待加载请求、关闭自动续播、清空内部队列和来源、重置三个策略。
    • 取消 MusicPlayerState 自己的协程作用域。
    • StreamPlayer.release() → 取消进度任务与自身作用域 → ExoPlayer.release()。
    • 触发条件是 MainScreen 退出组合，例如登录状态变为 Loading／Unauthenticated，或 Activity 的组合被销毁。
    • 当前没有在 MainActivity 中额外实现 onStop() 暂停逻辑；仅仅切到后台不等同于执行上述 onDispose。
